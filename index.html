v96 FINDING: sc=×1 but sc-spray-NOT-BUILT. Root cause confirmed:
slotchange is a MICROTASK — fires AFTER sync C++ returns. The freed old
bucket gets reclaimed synchronously by the rehash's own new-bucket alloc.
JS spray cannot interpose on a sync free+reuse.

v97 NEW APPROACH — FREEING SlotAssignmentData FIRST:

The UAF reads the freed BUCKET ARRAY to get SlotAssignmentData*,
then WRITES to the SlotAssignmentData object (which is still live).
We can't intercept the bucket-array read (sync). But we CAN intercept
the SlotAssignmentData WRITES if we free the SlotAssignmentData
itself before the trigger and reclaim it with our spray.

ATTACK A — SlotAssignmentData pre-free + reclaim:
1. Create shadow root, add named slot 'primary', assign nodes → SlotAssignmentData alloc'd
2. REMOVE the slot from shadow root → SlotAssignmentData freed
(HashMap entry removed, SlotAssignmentData released)
3. Spray objects same size as SlotAssignmentData → reclaim freed memory
4. Re-add slot, re-assign → SlotAssignmentData alloc'd at NEW addr (not our spray)
5. Trigger UAF → writes to NEW SlotAssignmentData → spray objects unaffected
— PROBLEM: Re-adding slot gets a NEW SlotAssignmentData, not the old one.
Our spray may occupy the old SlotAssignmentData addr but UAF won't write there.

ATTACK B — USE THE EXISTING assignedNodes AS RECLAIM TARGET:
The UAF zeroes slot->assignedNodes.m_data (a Vector<WeakPtr> internal buffer).
If the Vector had grown + reallocated its buffer, the OLD buffer is freed.
We spray at the OLD buffer size → reclaim it → UAF writes to our object? No,
the UAF writes to the NEW buffer (m_data points to current buffer).

ATTACK C — CRASH PATH (NULL-DEREF):
bmalloc on iOS normally does NOT zero freed chunks immediately.
But under GC pressure or certain allocation patterns, the 'decommit' path
zeroes pages returned to the OS. If old bucket page gets decommitted:
*slot = 0 (reading offset 0 of freed+zeroed 128B chunk)
slot->assignedNodes → nullptr->assignedNodes → crash at 0x0+8 or 0x0+0
We can stress-test the decommit path by:
a) Creating many rigs to exhaust bmalloc's per-class cache
b) Triggering large allocations between free and UAF read
c) Using madvise-pressure via many large ArrayBuffer allocs+frees

ATTACK D — TIMING WINDOW: ASYNC TRIGGER
What if we trigger the rehash NOT via insertBefore (sync) but via
a DIFFERENT path that defers the slot-assignment resolution?
WebKit slot assignment resolves lazily — if we force a layout AFTER
queuing many DOM mutations, the resolver may run once per microtask.
Between mutations and resolution: JS runs → we spray → THEN resolution reads.
