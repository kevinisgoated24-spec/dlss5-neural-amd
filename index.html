SVG UAF v41 — Bump exhaustion + WASM overlap + JSC heap bridge

ROOT CAUSE (v40 confirmed): bmalloc scavenger is DISABLED in WKWebView iOS (WKWebView::WebContent calls bmalloc::Scavenger::setThreadEnabled(false)). Freed IsoHeap pages stay in freelist but NEW allocs skip freelist and use bump allocator on the CURRENT page. slot[0]=1 ALWAYS = we're always getting bump-allocated on a fresh page. FIX: exhaust the bump allocator's current page so the NEXT alloc MUST hit the freelist. IsoHeap bump page is 16KB. sizeof(SVGNumber) ≈ 16 bytes → 1024 per page. After freeing N objects, we need to alloc EXACTLY (page_capacity - remaining_bump_slots) new objects so the bump allocator page runs out, then alloc ONE MORE → hits freelist → sees our tag. STRATEGY v41: 1. BMP1: bump-page exhaust — binary search for exact bump exhaustion count alloc A+B matrices: A = "filler to exhaust current bump page", B = "tagged test" free B, alloc A+1 new matrices → if A+1 pushes past bump boundary → B's freed slot reused 2. BMP2: feConvolveMatrix bump exhaustion (256 SVGNums per alloc = faster page fill) 3. JSB1: JS-heap bridge via WebAssembly.Memory wasm.Memory grows in 64KB pages. Its backing ArrayBuffer sits in FastMalloc. THEORY: wasm.Memory backing store could overlap with SVGNumber IsoHeap region in address space. If they're close, float32 ULP=512 oracle can detect them. 4. JSB2: Float64Array as heap probe — typed arrays use the C heap (not JSC MarkedSpace) Float64Array(N) allocates N*8 bytes in JavaScriptCore's butterfly heap but the backing store itself may use FastMalloc Test: alloc Float64Array, write patterns, free it (null ref), alloc SVGNumber, check if Float64Array addresses overlap with SVGNumber addresses 5. JSB3: ArrayBuffer detach probe — detach an ArrayBuffer and check if that memory gets reused by SVGNumber allocation (FastMalloc → IsoHeap boundary test) 6. WAS1: WebAssembly.Memory → SVGNumber address overlap oracle Grow wasm.Memory by 1 page (64KB). Read its backing buffer as Float32Array. Write our TAG to freed SVGNumber slot. Scan the entire wasm.Memory buffer for TAG. If found: the wasm backing store and IsoHeap are in the SAME address space region! This gives us a MEMORY SCANNER primitive. 7. WAS2: Reverse — SVGNumber float32 write, scan wasm.Memory Float32Array Write 9999999.0 to UAF slot, scan 64KB wasm buffer for that value. On hit: we know the OFFSET within wasm.Memory of the SVGNumber → address leak! 8. BRG1: JSC ArrayBuffer → IsoHeap proximity test Alloc ArrayBuffer(65536), get its byteLength. Then alloc SVGNumber, free ArrayBuffer. Use UAF write to write TAG to SVGNumber, then try to read TAG via a NEW ArrayBuffer of same size (hoping it reuses the freed ArrayBuffer backing store). 9. SZP1: sizeof(SVGNumber) probe via EXACT page fill bmalloc page = 16384 bytes. If sizeof=8: 2048/page. If sizeof=16: 1024/page. If sizeof=24: 682/page. Fill exactly 1024, 2048, 682 SVGNumbers, then alloc 1 more → if page boundary crossed → new alloc hits freelist Detect page boundary crossing by watching alloc timing (new page = new mmap call = slower) 10. GC1: force JSC GC → measure IsoHeap free behavior JSC GC runs when JS heap pressure hits threshold. On GC: JSC scans all live objects. Hypothesis: JSC GC also triggers bmalloc scavenger (they share the same process). Test: fill JS heap to trigger GC, then check IsoHeap freelist.
