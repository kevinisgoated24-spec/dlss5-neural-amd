rdar://179729192: ManualSlot WeakHashMap UAF during shrink-rehash.

CONTEXT:
ShadowRoot in manual-slot mode maintains a WeakHashMap:
m_manuallyAssignedSlotsForElementOrText : WeakHashMap<Node, HTMLSlotElement>
Maps: assigned node → the slot it was assigned to
Modified by: slot.assign(nodes) — each node added or removed updates this map

BUG TRIGGER — SHRINK PATH:
WTF::WeakHashMap (wraps WTF::HashTable) shrinks when:
live keyCount < tableSize / 8 (12.5% load threshold)
Example: add 16 nodes → capacity=32, then remove 14 → live=2 → 2/32=6.25% → shrink
During shrink: old bucket array freed, new smaller array allocated
If any iterator/reference holds a ptr into old array during this → UAF

TWO TRIGGER PATHS:
PATH A — slot.assign([]) direct removal:
1. slot.assign([n1,n2,...,n16]) → WeakHashMap grows to cap=32
2. slot.assign([n1]) → removes n2..n16 → live=1 → 1/32=3% → shrink
3. If WebKit is iterating the map during slot.assign() removal → UAF

PATH B — DOM removal (weak key GC):
1. slot.assign([n1,...,n32]) → WeakHashMap grows to cap=64
2. Remove n2..n28 from DOM → WeakPtrs become null → dead keys in map
3. WeakHashMap::removeDeadKeysIfNeeded() → removes dead entries
4. If live < tableSize/8 after cleanup → shrink → rehash → UAF

PATH C — CROSS-ASSIGN (key path for UAF):
The UAF in this bug likely occurs during resolveSlotsAfterSlotMutation
on a MANUAL shadow root. When iterating m_manuallyAssignedSlotsForElementOrText
and one iteration changes the map (reassignment) causing rehash.
The iterator holds a ref into the old bucket → dangling after rehash.
Trigger: two slots in same shadow root, slot A assigns node, slot B assigns
same node (forced reassignment during resolution) → one assignment clears
slot A's entry and adds to slot B → if map grows/shrinks → UAF.

SIGNAL DETECTION:
Unlike NamedSlot UAF, ManualSlot UAF might CRASH (null-deref) rather than
silently write, if the iterator reads a zeroed freed chunk.
Detection: try/catch around trigger. THREW = UAF crash = confirmed.
Also: check assignedElements() before/after for unexpected state changes.

KEY MATH for shrink threshold:
tableSize=8: shrinks when live < 1 (removing all entries from size-8 map)
tableSize=16: shrinks when live < 2
tableSize=32: shrinks when live < 4
tableSize=64: shrinks when live < 8
tableSize=128: shrinks when live < 16
→ Best target: grow to cap=64 (need 9+ nodes), remove all but 7 → 7/64=11% → shrink
